# GNU sha256sum on SrvrOS

This port builds standalone `sha256sum` from GNU Coreutils 9.12. It uses
GNU `src/cksum.c` with `HASH_ALGO_SHA256=1`, GNU’s bundled SHA-256 stream
and the support sources selected for the SrvrOS SDK. Preparation works on
a generated copy. The release and detached signature are stored under
`upstream/coreutils`. The release contains GNU’s license notices.

The release archive SHA-256 is
`a480198559733e9b3da999e90543ac6f888a2caa544d8d664c5a1f17e528e210`.
The detached signature was verified against the release key
`6C37DC12121A5006BC1DB804DF6FD971306037D9`.

The C-locale profile hashes explicit regular files or finite standard input.
Use `-b` or `-t` to select the GNU mode marker. `-c` consumes one explicit
manifest, with `-` selecting standard input. The untagged format admits
both mode markers and GNU escaping for backslash, LF and CR when representable
on the target filesystem. The manifest is capped at 256 KiB and 4096 physical
records. The decoded pathname cap is 1023 bytes. Comments and blank lines
count toward the input limits. A check needs a correctly formatted entry and
fails on malformed records, missing files, I/O errors or digest mismatches.
When the manifest comes from stdin it cannot also name stdin as a data source.

The GNU hashing loop streams through a 32 KiB buffer. The port uses
cooperative INT and TERM checkpoints in source reads, hashing and manifest
processing. The profile excludes tagged manifests, recursive file discovery
and the other Coreutils commands. The existing `cksum` and `sum` are independent.

Build `build/userspace/sha256sum.elf` from the matched OS checkout. The
selected gnulib headers were generated by the Coreutils cross-configure for
`x86_64-unknown-none` against the SrvrOS SDK with threads, NLS and OpenSSL
turned off. The command explicitly uses SDK stdio for the supported integer
and string formats and handles stream errors through SDK status and close.
The SDK supplies the target hostname limit.

On OS `77b0c7cb`, the native GNU 9.12 reference and disposable SrvrOS guest
agree on ten scoped digest or verification cases. The guest exercised eleven
refusals with distinct byte and record limits, a late nonblocking input
error with empty stdout, and read-only output failure. INT and TERM returned
130 and 143 after pipe consumption. Private mapped user bytes measured
2,314,240 at both 32 KiB and 1,081,344 bytes of input, excluding kernel and
shared mappings. This measurement is from two live checkpoints. Two clean
component builds on matching SDK objects produced identical selected objects
and application and probe ELFs. Guest filesystem checks were clean.
